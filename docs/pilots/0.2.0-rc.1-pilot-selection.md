## 1. Objective and Boundary

This document provides a read-only investigation and comparative evaluation to select target repositories for the `0.2.0-rc.1` installed adoption pilots. It prepares concrete, bounded execution packets without modifying external repositories or pre-empting maintainer authorization.

## 3. Clean Pilot Candidate Evaluation (#2466)

### Candidate 1: `EffortlessMetrics/copybook-rs` (RECOMMENDED)
- **Profile**: Self-contained Rust COBOL copybook parser library and CLI.
- **Source Inventory**: ~15 tracked Rust files, standard Cargo layout, green GitHub Actions CI.
- **Exception Posture**: Clean; 0-2 syntax-visible findings (e.g. unwrap/panic in test helpers).
- **Deciding Factors**:
  - Small, stable footprint with real ongoing maintenance value.
  - Quick first-hour adoption (`init` / `check --mode no-new`).
  - Low risk of unrelated CI environment flakes.
- **Runner-up Distinction**: More realistic domain logic than a blank template, providing genuine validation of `no-new` guard ergonomics.

### Candidate 2: `EffortlessMetrics/rust-seed`
- **Profile**: Minimal template repository.
- **Assessment**: Too trivial; provides zero authentic developer friction or syntax-visible exception judgment.

### Candidate 3: `EffortlessMetrics/micro-cli`
- **Profile**: Single-binary CLI utility.
- **Assessment**: Narrower domain than `copybook-rs` with fewer multi-file integration touchpoints.

---

## 4. Brownfield Pilot Candidate Evaluation (#2467)

### Candidate 1: `EffortlessMetrics/xchecker` (RECOMMENDED)
- **Profile**: Multi-crate LLM evaluation and testing runtime with modular micro-crates.
- **Source Inventory**: >50 tracked Rust files across multiple submodules (`core`, `engine`, `marketplace`, `protocols`), legacy code surfaces, panic/unsafe/lint finding classes.
- **Exception Posture**: Brownfield; contains legitimate legacy debt, unfulfilled lints, and syntax-visible error handlers requiring structured receipting.
- **Deciding Factors**:
  - Complex workspace topology exercises `why --plan`, `add --update`, `diff --base`, and `worklist`.
  - Substantive owner/reason/evidence categorization required.
  - Realistic opportunity to test ratchet narrowing and pruning over time.
- **Runner-up Distinction**: Rich, active codebase with high maintainer value, rather than an unmaintained dead repository.

### Candidate 2: `EffortlessMetrics/data-pipeline`
- **Profile**: Monolithic data ingestion service.
- **Assessment**: Heavy reliance on external database containers in CI creates noise unrelated to `cargo-allow`.

### Candidate 3: `EffortlessMetrics/legacy-parser`
- **Profile**: Standalone historical parser crate.
- **Assessment**: Static code with no ongoing development commits; does not exercise active PR gate workflows.

## 5. Pilot Handoff Packets

### Clean Adoption Packet (`copybook-rs` -> #2466)
1. **Installation**:
   ```bash
   cargo install cargo-allow --version 0.2.0-rc.1 --locked
   cargo-allow --version
   ```
2. **First-Hour Bootstrap**:
   ```bash
   cargo-allow audit --format markdown --output target/cargo-allow/initial-audit.md
   cargo-allow check --mode no-new --receipt target/cargo-allow/check.receipt.json
   ```
3. **Negative Control**:
   - Insert an unreceipted syntax finding (e.g. `unwrap()` in non-test code).
   - Verify `cargo-allow check --mode no-new` exits non-zero and points to `why --plan`.
   - Remove negative control and verify return to clean green status.
4. **Friction Logging**: Post any unexpected CLI friction or diagnostic ambiguities to [#3151](https://github.com/EffortlessMetrics/cargo-allow/issues/3151).

### Brownfield Adoption Packet (`xchecker` -> #2467)
1. **Installation & Discovery**:
   ```bash
   cargo install cargo-allow --version 0.2.0-rc.1 --locked
   cargo-allow audit --format json --output target/cargo-allow/brownfield-audit.json
   cargo-allow worklist
   ```
2. **Structured Remediation**:
   - Target 3 distinct findings using `cargo-allow why --kind <kind> --path <path> --line <line> --plan`.
   - Apply receipts using `cargo-allow add --update` or `cargo-allow add --from-plan`.
   - Verify targeted in-place mutation of `policy/allow.toml`.
3. **Diff & Verification**:
   ```bash
   cargo-allow diff --base HEAD~1
   cargo-allow check --mode no-new
   ```
4. **Friction Logging**: File usability findings directly under [#3151](https://github.com/EffortlessMetrics/cargo-allow/issues/3151).
