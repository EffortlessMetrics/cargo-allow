## Operator value

```text
doctor / audit
→ why --kind ... --path ... --line ...
→ add --update (or add --from-plan)
→ check --mode no-new
→ list / explain / worklist
→ diff --base <base>
```

These commands support source finding diagnosis, explicit receipt updates,
and rechecks. The remaining cross-command, error-guidance, and first-use
corrections below must be qualified before claiming a consistent final loop.

- Non-Rust semantic sensors (workflow YAML, TOML, shell parsing) are future
  work.

## Scanner capability contract

The 0.2.0 source candidate exposes the checked sensor catalog through the
installed binary:

```bash
cargo-allow capabilities --format json
```

The JSON contract is `cargo-allow.sensor-capabilities.v1`, generation 1. It
describes the source-tree sensors, their supported and excluded claims, and
their limitations. It is a discovery and claim-boundary surface, not a
release-publication or semantic-analysis guarantee. In particular, the
catalog does not claim compilation, type analysis, macro expansion, MIR,
runtime behavior, or test adequacy. The catalog and support metadata are
tracked by [#2570](https://github.com/EffortlessMetrics/cargo-allow/issues/2570)
and [docs/support-matrix.toml](../support-matrix.toml).

## Performance evidence

The [performance ledger](../performance-budgets.md) records a 2026-07-18
Windows debug baseline of approximately 22,600 ms for full `audit` and 240 ms
for single-file `why` on this repository. Those historical measurements do
not establish a universal speedup or a current final-candidate result.

The hosted Linux release-build `operator-latency` job now enforces a 60,000 ms
catastrophic ceiling per measured command and configured artifact payload
ceilings. Its V4 receipt retains binary/fixture identity, timings, digests,
and artifact/semantic-artifact byte counts
([#4403](https://github.com/EffortlessMetrics/cargo-allow/issues/4403),
[#4416](https://github.com/EffortlessMetrics/cargo-allow/pull/4416)). Advisory
latency and agent-read targets remain distinct from these enforced ceilings.
[#4339](https://github.com/EffortlessMetrics/cargo-allow/issues/4339) owns the
remaining command and one-file-loop coverage; the full check JSON payload gap
is [#4374](https://github.com/EffortlessMetrics/cargo-allow/issues/4374).

## Known Limitations

- The source scanner observes source-tree/source-syntax evidence without
  executing repository code or invoking Cargo, rustc, Clippy, build scripts,
  or proc macros.
- `why` fast path is advisory; `add` keeps the full pipeline.
- The [manifest wrapper](../../scripts/generate-release-manifest.sh) uses a
  bounded Python encoder and calls the production Rust release-identity and
  publication-reconciliation authorities. This implemented delegation does
  not establish a complete final release: preserved publication receipts,
  typed aggregate admission, actual draft-asset readback, and finalization
  remain required under #2497/#3761/#3726.
- Candidate platform and install observations remain limited to their exact
  bytes and tested environments. The
  [support matrix](../support-matrix.toml) records evidence and unresolved
  support-policy decisions; it does not make broader compatibility promises.

## Rollback

For consumers returning to the stable baseline, explicitly reinstall the
previously qualified `0.1.11` version:

```bash
cargo install cargo-allow --version 0.1.11 --locked --force
```

A registry yank is a separate incident decision, not this consumer rollback.
Do not silently yank RC.1, move an observed release tag, or reuse a published
version for corrected contents. Partial publication and recovery retain the
original incident under
[#2509](https://github.com/EffortlessMetrics/cargo-allow/issues/2509); repairs
that require new release bytes need a fresh version, freeze, and authorization.
