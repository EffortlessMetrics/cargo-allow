# 0.1.1 Release Record

This records the completed 0.1.1 patch release after the published `0.1.0`
crates.io release.

The release is irreversible once packages are published. If a published package
is wrong, the rollback path is to yank the affected version and publish a fixed
patch release. Do not publish from a dirty tree.

## Target Claim

The 0.1.1 release may keep the 0.1.x claim:

```text
cargo-allow inventories syntax-visible source exceptions and checks them
against a policy ledger.
```

It may also say that current reports, receipts, command artifacts, worklists,
and PR summaries carry the source-tree claim boundary and scanner limitations.

It must not claim macro-expanded, type-aware, MIR-level, build-aware,
control-flow, data-flow, unsafe-proof, test-adequacy, or coverage-proof
analysis.

## Release Scope

0.1.1 is a patch release for product hardening merged after 0.1.0:

- JSON artifact contract hardening, saved-output coverage, and shared
  source-tree claim-boundary rendering.
- Source exception inventory summaries in human, Markdown, JSON, and HTML audit
  reports so first-run exception posture is visible without re-aggregating raw
  findings.
- Diff posture reporting for source finding changes, policy weakening, and
  policy improvements.
- Evidence diagnostics, broken local evidence visibility, and missing-evidence
  policy-health counts.
- Generated baseline proposals now separate unsafe `baseline_debt` counts from
  the aggregate proposed baseline count so unsafe adoption debt remains visible
  until reviewed with real evidence.
- Worklist routing improvements for baseline debt, broad scopes, missing
  evidence, source-tree path slices, owner/classification filters, and
  risk/difficulty queues.
- Legacy migration and compat polish for source-tree policy ledgers.
- CI and README install guidance that distinguishes the published release from
  current `main`.
- Test and module organization hardening that reduces future release risk.
- Source-location hint hardening that documents and schema-tests one-based
  review/navigation positions, with Rust source columns reported as character
  columns rather than byte offsets.
- External evidence-tool boundary disclosure in JSON claim-boundary and scanner
  limitation artifacts, making clear that dependency policy, audit,
  unsafe-review, ripr, and coverage tools may provide evidence but are not
  executed by cargo-allow scans.
- Proof-command boundary hardening for worklist and explain artifacts, keeping
  agent-facing follow-up commands inside the standalone `cargo-allow` CLI rather
  than external build or evidence tooling.
- Shared `common.v1` schema fragment coverage for allow entries, source-finding
  rows, stale-prune rows, evidence diagnostics, and worklist filters/items so
  command artifact contracts stay aligned while individual schemas remain
  portable.
- Setup diagnostics now report the loaded policy schema version, policy name,
  owner, and status in human and JSON `doctor` output so release checks show
  which policy contract and ledger state were validated.
- Human `explain` and `worklist` output now surfaces evidence diagnostic detail
  for retained entries and broken or weak evidence work items without requiring
  JSON parsing.

Non-goals for 0.1.1:

- No claim of build-aware, Cargo-metadata, Clippy, rustc, proc-macro, or
  proof-tool execution.
- No source-tree policy broadening to make release checks pass.
- No laundering generated `baseline_debt` into reviewed approval.
- No compatibility claim for external dogfood lanes that have not been
  revalidated during the release turn.

## Publish Order

Publish internal crates in dependency order:

```text
1. allow-core
2. allow-policy
3. allow-inventory
4. allow-files
5. allow-rust
6. allow-match
7. allow-report
8. allow-policy-legacy
9. allow-diff
10. cargo-allow
```

This ordering matters because dependent crates use crates.io after publication.
A dependent crate's `cargo publish --dry-run` may not fully verify until its
internal registry dependencies are already published and visible in the index.

Before publishing anything, `allow-core` can be dry-run independently because it
has no internal registry dependency:

```bash
cargo publish --dry-run -p allow-core --locked
```

Later dependent dry-runs should remain inside the per-crate publish loop below
so each internal `0.1.1` dependency is already visible before the next package
is verified. If you stop after a dry-run without publishing, remove generated
package and cargo-allow artifacts before leaving the repo:

```bash
powershell -NoProfile -Command 'Remove-Item -LiteralPath target\package,target\cargo-allow -Recurse -Force -ErrorAction SilentlyContinue'
```

## Per-Crate Loop

For each crate in publish order:

```bash
cargo publish --dry-run -p <crate> --locked
cargo publish -p <crate> --locked
```

After each publish, wait for crates.io/index visibility before dry-running the
next dependent crate. Verify with:

```bash
cargo info <crate>
```

If crates.io visibility lags, wait and retry the next dry-run. Do not edit
manifests or broaden policy to force progress.

## Rollback

Crates.io versions are immutable. If publication is wrong:

```bash
cargo yank <crate> --version 0.1.1
```

Then prepare and publish a patch release. Do not reuse `0.1.1` for corrected
contents.
