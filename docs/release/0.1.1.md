# 0.1.1 Release Prep

This is a release-prep handoff for the next patch release after the published
`0.1.0` crates.io release. It does not record a completed publication.

The release is irreversible once packages are published. If a published package
is wrong, the rollback path is to yank the affected version and publish a fixed
patch release. Do not publish from a dirty tree.

## Target Claim

The 0.1.1 release may keep the 0.1.x claim:

```text
cargo-allow inventories syntax-visible source exceptions and checks them
against a policy ledger.
```

It may also say that current reports, receipts, command artifacts, worklists,
and PR summaries carry the source-tree claim boundary and scanner limitations.

It must not claim macro-expanded, type-aware, MIR-level, build-aware,
control-flow, data-flow, unsafe-proof, test-adequacy, or coverage-proof
analysis.

## Candidate Scope

Use 0.1.1 as a patch release for product hardening already merged after 0.1.0:

- JSON artifact contract hardening, saved-output coverage, and shared
  source-tree claim-boundary rendering.
- Diff posture reporting for source finding changes, policy weakening, and
  policy improvements.
- Evidence diagnostics, broken local evidence visibility, and missing-evidence
  policy-health counts.
- Worklist routing improvements for baseline debt, broad scopes, missing
  evidence, source-tree path slices, owner/classification filters, and
  risk/difficulty queues.
- Legacy migration and compat polish for source-tree policy ledgers.
- CI and README install guidance that distinguishes the published release from
  current `main`.
- Test and module organization hardening that reduces future release risk.
- Source-location hint hardening that documents and schema-tests one-based
  review/navigation positions, with Rust source columns reported as character
  columns rather than byte offsets.

Non-goals for 0.1.1:

- No claim of build-aware, Cargo-metadata, Clippy, rustc, proc-macro, or
  proof-tool execution.
- No source-tree policy broadening to make release checks pass.
- No laundering generated `baseline_debt` into reviewed approval.
- No compatibility claim for external dogfood lanes that have not been
  revalidated during the release turn.

## Preflight

Run from repository root on `main` after all release-prep PRs are merged:

```bash
rtk git status --short --branch
rtk git fetch --prune
rtk git pull --ff-only
rtk cargo fmt --all --check
rtk cargo clippy --workspace --all-targets -- -D warnings
rtk cargo test --workspace
rtk cargo run -p cargo-allow -- allow check --mode no-new \
  --format markdown \
  --receipt target/cargo-allow/check.receipt.json \
  --output target/cargo-allow/check.md
rtk cargo package --list --workspace
```

Latest post-merge cargo-allow posture for this handoff:

```text
59 matched, 0 new, 0 stale
488 source-tree inventory files scanned via git_tracked
```

Recheck that posture immediately before publishing; policy and docs changes can
change the scanned count without being release blockers.

## Version Bump

This release-prep branch updates the workspace package version, internal
workspace dependency requirements, and lockfile package versions from `0.1.0`
to `0.1.1`:

```text
Cargo.toml
Cargo.lock
```

Before publishing, verify those files still carry `0.1.1`. Do not publish if a
later branch has reverted or partially changed the version set.

Do not update README or CI install examples to `0.1.1` until the crates.io
publish has completed and `cargo search cargo-allow --limit 1` confirms the new
version is visible.

## Publish Order

Publish internal crates in dependency order:

```text
1. allow-core
2. allow-policy
3. allow-inventory
4. allow-files
5. allow-rust
6. allow-match
7. allow-report
8. allow-diff
9. allow-policy-legacy
10. cargo-allow
```

This ordering matters because dependent crates use crates.io after publication.
A dependent crate's `cargo publish --dry-run` may not fully verify until its
internal registry dependencies are already published and visible in the index.

## Per-Crate Loop

For each crate in publish order:

```bash
rtk cargo publish --dry-run -p <crate> --locked
rtk cargo publish -p <crate> --locked
```

After each publish, wait for crates.io/index visibility before dry-running the
next dependent crate. Verify with:

```bash
rtk cargo info <crate>
```

If crates.io visibility lags, wait and retry the next dry-run. Do not edit
manifests or broaden policy to force progress.

## Final Verification

After `cargo-allow` is published:

```bash
rtk cargo search cargo-allow --limit 1
rtk cargo info cargo-allow
rtk cargo install cargo-allow --version 0.1.1 --locked --root target/cargo-allow-install --force
rtk .\target\cargo-allow-install\bin\cargo-allow.exe --help
rtk .\target\cargo-allow-install\bin\cargo-allow.exe check --mode no-new \
  --format markdown \
  --receipt target/cargo-allow/check.receipt.json \
  --output target/cargo-allow/check.md
```

Then update README and CI examples from `0.1.0` to `0.1.1` in a follow-up PR.

If tagging is selected for the release, create the tag only after the published
crate set and install smoke are verified. Do not create or move historical tags
as part of this runbook.

## Rollback

Crates.io versions are immutable. If publication is wrong:

```bash
rtk cargo yank <crate> --version 0.1.1
```

Then prepare and publish a patch release. Do not reuse `0.1.1` for corrected
contents.
