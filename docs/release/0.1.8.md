# 0.1.8 Preview Release Notes

This is a release-candidate record for a future `0.1.8` patch release after the
published `0.1.7` crate set.

Workspace package versions have been bumped to `0.1.8` for release-candidate
validation. No crate has been tagged, published, install-smoke verified, or
verified on crates.io for `0.1.8` yet. Public install examples should keep
pinning the latest published `0.1.7` release until publication completes.

The latest completed release record is [0.1.7](0.1.7.md).

## Target Claim

The 0.1.8 release should keep the 0.1.x default claim:

```text
cargo-allow inventories syntax-visible source exceptions and checks them
against a policy ledger.
```

It may additionally say that the opt-in `spec-system` preview profile has a
smoother first-hour adoption path: generated profile files no longer create an
immediate active-goal readiness finding before a repository has registered a
real proposal/spec/plan graph.

It must not claim that the profile is stable, default-enabled, or proof
executing. It must not claim macro-expanded, type-aware, MIR-level,
build-aware, control-flow, data-flow, unsafe-proof, test-adequacy,
coverage-proof, release-readiness, or semantic-correctness behavior.

## Preview Scope

0.1.8 is a cleanup candidate for friction found while self-hosting the
published 0.1.7 binary:

- `cargo-allow init --profile spec-system` now generates
  `active_goal_required = false` in `policy/spec-system.toml`, so a new
  repository can get a clean first-hour `doctor --profile spec-system` result
  before it has registered real proposal/spec/plan/support-tier/closeout
  artifacts.
- Generated `.codex/goals/active.toml` explains that it is placeholder
  execution state and that active-goal enforcement should be enabled after the
  real graph is registered.
- `doctor --profile spec-system` reports the active-goal readiness check as
  ready when `active_goal_required = false`, with a message explaining that
  validation is optional.
- Spec-system Markdown reports use one neutral `Findings` section and a
  `Findings` metric row instead of repeating mode-specific headings such as
  `Advisory Findings`.
- Adoption docs explain when to flip `active_goal_required = true`.

## Non-Goals

- Do not make spec-system part of default `cargo-allow check`.
- Do not promote the spec-system support-tier row beyond Advisory.
- Do not add new lint rules in this release.
- Do not run proof commands from cargo-allow's own scan.
- Do not call GitHub APIs or network services from the scanner.
- Do not invoke Cargo, rustc, Clippy, build scripts, proc macros, ripr,
  unsafe-review, coverage, or repository code from the scanner.
- Do not claim stable support-tier status for the spec-system profile.

## Claim Boundary

The spec-system profile is structural source-tree graph validation. It may parse
TOML and Markdown and inspect repository files. It may verify IDs, paths,
statuses, links, support-tier proof fields, active-goal references, and closeout
links.

It must not execute proof commands, call GitHub APIs, inspect external PR state,
run Cargo, rustc, Clippy, build scripts, proc macros, ripr, unsafe-review,
coverage, or network checks as part of the cargo-allow scan.

## Rollback

Before publication, rollback is a normal revert of the release-candidate commit.

After publication, crates.io versions are immutable. If a published package is
wrong:

```bash
rtk cargo yank <crate> --version 0.1.8
```

Then prepare and publish a fixed patch release. Do not reuse `0.1.8` for
corrected contents.
