## Plan: `add --update` — safe in-place ledger mutation

**Problem:** `cargo-allow add ... --write policy/allow.toml` fails in the ordinary case because the write target exists. `add` is a propose-style command: it renders the *entire* policy and routes it through `write_file_no_overwrite`, which uses `OpenOptions::create_new` and rejects with `"{} already exists; use --force to overwrite"` (`io.rs:149-152`, test `add_tests.rs:635-684`). Worse, `--force` is the wrong mental model for appending one entry — it backs up the whole ledger to `.bak` and rewrites everything, when the operator just wants to add one receipt.

Meanwhile `refresh` and `prune` already mutate `policy/allow.toml` in place correctly: they resolve the live config path, acquire a `MutationLock`, load→mutate→validate→`write_file` (atomic temp+rename, `io.rs:36-92`), and emit a mutation receipt. We mirror that pattern exactly.

**Decisions (confirmed):**
- New boolean `--update` flag on `add`. With it, `add` updates the live ledger in place (Model B). The existing `--write <PATH>` candidate-file behavior is untouched.
- Evidence mode stays `load_world` (Abort/strict). New receipts shouldn't land in a ledger with broken evidence refs.

### Change 1 — `crates/cargo-allow/src/add_args.rs`: add `--update`

Add a boolean field, mirroring refresh/prune's `--write: bool` shape:
```rust
/// Update the live policy in place instead of printing/writing a candidate file.
/// Resolves the discovered policy/allow.toml, validates the full result, and
/// atomically replaces it. Mutually exclusive with --write.
#[arg(long)]
pub update: bool,
```
Add a guard in `cmd_add`: `--update` and `--write` are mutually exclusive (return a clear error if both set), matching refresh's `--dry-run`/`--write` exclusivity (`refresh.rs:28-32`).

### Change 2 — `crates/cargo-allow/src/add.rs`: the in-place write branch

The load→mutate→validate tail (`add.rs:166-176`) stays. Change only the write dispatch. Today:
```rust
if let Some(path) = &args.write {
    write_file_no_overwrite(path, &rendered, args.force)?;
} else {
    println!("{rendered}");
}
```
Becomes a three-way dispatch:
```rust
if args.update {
    // Resolve live policy path (already proven by load_world; re-resolve for the write target).
    let policy_path = config_path(&root, args.config.as_deref())
        .ok_or_else(|| CargoAllowError::new("no policy config found to update; run `cargo-allow init`"))?;
    write_file(&policy_path, &rendered)?;  // atomic temp+rename, mirrors refresh/prune
} else if let Some(path) = &args.write {
    write_file_no_overwrite(path, &rendered, args.force)?;  // candidate file, unchanged
} else {
    println!("{rendered}");
}
```
**Mutation lock:** extend the `mutation_target` resolution (`add.rs:46-56`) so `--update` also acquires the lock on the live config path, exactly like `--write` does. The lock must cover the in-place write so concurrent `add --update` / `refresh` / `prune` can't race.

**Summary/receipt `result` field:** `add_mutation_receipt` (`add_render.rs:15`) keys `"written"` vs `"stdout"` off whether there's a policy output. For `--update`, pass the resolved live path as the policy output so the receipt reports `"written"` with the real config source. This threads through the existing `args.write.as_deref()` plumbing in the summary builders — for `--update`, substitute the resolved `policy_path`.

### Change 3 — Tests: `crates/cargo-allow/src/add_tests.rs`

- **Keep** `cmd_add_rejects_write_to_existing_output_without_force` (L635-684) unchanged — it tests `--write <PATH>`, whose semantics don't change.
- **Add** `cmd_add_update_writes_entry_into_live_policy`: seed a real `policy/allow.toml` with 1+ existing entries, run `add --update --kind ... --path ... --line ... --owner ... --reason ...`, assert (a) the file now contains the new `[[allow]]` block, (b) the existing entries are preserved byte-for-byte in the rendered output, (c) `validate_policy` passes on the result, (d) the mutation receipt reports `result: "written"`.
- **Add** `cmd_add_update_rejects_when_write_also_set`: assert `--update` + `--write` together errors clearly.
- **Add** `cmd_add_update_requires_existing_policy`: assert `--update` with no discovered config errors with the init hint.

### Change 4 — `why` suggested plan: use `--update` not `--write`

`why_render.rs:106-122` (`add_receipt_plan`) currently renders `--write policy/allow.toml` — the command that fails in the normal case. Change it to render `--update` (no path arg), so the suggested command actually works against an existing ledger. The placeholder fields (`--owner <owner>`, `--reason ...`, `--evidence <ref>`) remain — those are the human-judgment fields, by design.
